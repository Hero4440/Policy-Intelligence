Create `src/mcp/tools/utils/llm_client.ts`:

**LLM client** — Anthropic Claude wrapper with evidence-grounding prompt.

Export `answerWithGrounding(question: string, evidenceSnippets: EvidenceItem[], entities: ExtractedEntities): Promise<string>`:

1. Initialize Anthropic client: `new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY })`. Use `maxRetries: 2` and `timeout: 30000`.
2. Format evidence for injection: number each snippet as `[E0]`, `[E1]`, etc. Include the snippet text, source policy title, and section.
3. Build system prompt instructing Claude to:
   - Answer the question using ONLY the provided evidence snippets
   - Cite every factual claim with `[E0]`, `[E1]`, etc. inline
   - Transitional/framing sentences are OK without citations
   - DO NOT include any facts not supported by evidence
   - If cross-payer comparison is possible, synthesize but cite each claim
   - If evidence is insufficient for part of the answer, explicitly state what's missing
4. Call `client.messages.create()` with:
   - Model: `claude-sonnet-4-20250514` (configurable via `process.env.ANTHROPIC_MODEL` with this as default)
   - `max_tokens: 1024`
   - `temperature: 0` (deterministic for evidence grounding)
   - System prompt + user message with the question
5. Extract text from response. If API error, throw with descriptive message.
6. Return the raw LLM text (claim validation happens in the validator).

Handle errors: wrap in try/catch, distinguish between `Anthropic.APIError` (throw LLM API error with status/message) and other errors (rethrow). If `ANTHROPIC_API_KEY` is not set, throw immediately with message: "ANTHROPIC_API_KEY environment variable is required for LLM-powered Q&A".

Create `src/mcp/tools/utils/claim_validator.ts`:

**Claim validator** — parses LLM response into claims, validates evidence references, strips ungrounded claims.

Export `GroundedClaim` interface:
```typescript
interface GroundedClaim {
  claim_id: string;      // e.g., "claim_0"
  claim_text: string;    // The sentence text
  evidence_refs: string[]; // e.g., ["E0", "E2"]
}
```

Export `extractAndValidateClaims(llmResponse: string, evidenceCount: number): { validClaims: GroundedClaim[], filteredCount: number, cleanedAnswer: string }`:

1. Split LLM response into sentences (split on `.`, `!`, `?` followed by space or end of string — preserve citation brackets).
2. For each sentence, extract evidence references matching `/\[E(\d+)\]/gi`.
3. Sentences WITH valid references (index < evidenceCount) are "grounded claims" — keep them.
4. Sentences WITH invalid references (index >= evidenceCount) are "ungrounded" — strip them.
5. Sentences WITHOUT any references are "transitional" — keep them (per user decision: transitional/framing OK).
6. Build `cleanedAnswer` from kept sentences (grounded + transitional), joining with spaces.
7. Strip citation markers from cleanedAnswer for human readability (the structured_result will have the claim-to-evidence mapping).
8. Return: `validClaims` array, `filteredCount` (number of stripped sentences), `cleanedAnswer` (human-readable).

**Create `src/mcp/tools/ask_policy_question.ts`** — the main hybrid Q&A tool.

Export `registerAskPolicyQuestion(server: McpServer): void`:

Register tool `ask_policy_question` with:
- Description: "Answer natural language questions about loaded medical insurance policies. Uses hybrid approach: tries deterministic lookup first, falls back to LLM with evidence grounding for complex questions. Every factual claim is validated against loaded policy evidence. Returns answer with evidence citations, confidence level, and routing metadata."
- Input schema: `askPolicyQuestionInput.shape`

Handler flow:

1. **Extract entities**: `extractEntities(question)`

2. **Route query**: `routeQuery(question, entities)`

3. **Handle by route**:

   **Route: `out_of_scope`**:
   Return `buildStandardResponse()` with:
   - answer: "This question is outside the scope of loaded insurance policies. I can answer questions about coverage criteria, prior authorization, step therapy, and drug policy comparisons."
   - structured_result: `{ route: "out_of_scope", detected_entities: { drug: null, payer: null } }`
   - evidence: `[]`
   - confidence: `"LOW"`

   **Route: `insufficient_evidence`**:
   Build loaded scope string from `getAllPolicies()` listing each policy's payer and drug family.
   Return `buildStandardResponse()` with:
   - answer: `"Insufficient evidence to answer this question. ${route.reason}. Loaded policies: ${loadedScope}"`
   - structured_result: `{ route: "insufficient_evidence", detected_entities: { drug: entities.drug, payer: entities.payer }, loaded_policies: loadedScopeArray }`
   - evidence: `[]`
   - confidence: `"LOW"`

   **Route: `deterministic`**:
   Execute the Phase 2 tool internally. Do NOT call the MCP tool registration — instead, import the underlying logic:
   - For `list_policies`: import the handler logic from list_policies.ts or re-call via the same policy store APIs
   - For `get_policy_summary`: use `findPolicy()` + build summary response
   - For `compare_drug_across_payers`: use `findPoliciesByDrug()` + build comparison

   **Simpler approach (recommended):** Since Phase 2 tools are registered on the same MCP server but we can't easily call them internally, replicate the core logic inline:
   - `list_policies` pass-through: call `getAllPolicies()`, filter by entities, return via `buildStandardResponse()` with route info added to structured_result
   - `get_policy_summary` pass-through: call `findPolicy(entities.payer, entities.drug)`, use `extractEvidenceArray()`, build summary response with route info
   - `compare_drug_across_payers` pass-through: call `findPoliciesByDrug(entities.drug)`, build comparison with route info

   Add `route: "deterministic"` and `detected_entities` to structured_result. Confidence: `"HIGH"`.

   **IMPORTANT alternative (preferred for DRY):** Import and call the existing Phase 2 tool handler functions directly if they are exported as standalone functions (check the tool files). If the tool handlers are only accessible via MCP registration callbacks, extract the core logic into shared functions that both the tool registration and this Q&A tool can call. This is a Claude discretion decision — pick the approach that minimizes code duplication.

   **Route: `llm`**:
   1. Retrieve evidence: `retrieveEvidence(entities, extractQuestionKeywords(question))`
   2. If zero evidence items returned, switch to `insufficient_evidence` response (per user decision)
   3. Call LLM: `answerWithGrounding(question, evidence.items, entities)`
   4. Validate claims: `extractAndValidateClaims(llmResponse, evidence.items.length)`
   5. If zero valid claims AND zero transitional sentences, return `insufficient_evidence`
   6. Build extended evidence: map each `EvidenceItem` with optional `claim_id` linking to the claim that references it
   7. Determine confidence: `filteredCount > 0 ? "LOW" : "MEDIUM"`
   8. Build response via `buildStandardResponse()` with:
      - answer: `cleanedAnswer`
      - structured_result: `{ route: "llm", detected_entities, grounded_claims: [...], filtered_claims: filteredCount, note (if filtered) }`
      - evidence: extended evidence array with claim_id links
      - confidence: tiered as above

   Wrap LLM path in try/catch. On LLM error (API key missing, API error, timeout): return `buildErrorResponse()` with descriptive message and suggestion to check ANTHROPIC_API_KEY.
